User guide

DIGIBAT remote sync

End-to-end trace of how the /digibat page connects to the Imperial DIGIBAT API, downloads cycling files, and lands them in the same PostgreSQL + Parquet storage as browser uploads. Sync is feasible in the shipped build; hardening for production use is outstanding.

Related pages. Ingestion pipeline documents the shared ingest_cycling_file path; Data model lists DIGIBAT provenance columns; REST API documents /api/digibat/* routes.

Terminology

TermMeaning in CellSeer
CollectionRemote DIGIBAT grouping (lab campaign). Listed via GET /api/digibat/collections; synced by collection id.
RefcodeStable remote cell identifier (e.g. digibat:VAOGWT). Mapped in digibat_cell_map; survives upstream display-name renames.
source_file_idRemote file immutable id. Tracked in digibat_file_map for incremental skip/resync.
Continuation groupMulti-part exports (_C01, _C02, …) grouped by group_continuation_files() and ingested in one ingest_cycling_file call.
Sync runObservability row in digibat_sync_run — status running → done | error. Mode is sync (normal) or dry-run.

PostgreSQL tables

TablePurposeKey columns
digibat_connection Per-project API credentials project_id PK, base_url, api_key (nullable), key_source (env | user), created_at, updated_at
digibat_cell_map Remote refcode → local cell_id (project_id, remote_refcode) PK, remote_item_id, cell_id (FK→cell), last_seen_at
digibat_file_map Per remote file ingest state (project_id, source_file_id) PK, remote_refcode, filename, source_version, cell_id (FK→cell, ON DELETE SET NULL), last_status, last_error, last_synced_at, deleted_at
digibat_sync_run Run history + totals JSON id (UUID), project_id, mode (sync|dry-run), status (running|done|error), collection_ids_json, totals_json, error_message, started_at, completed_at

After successful ingest, data also appears in the standard cell, dataset, and data_lake/ tables — same as upload. On cell rows: source_system='digibat', source_refcode, source_item_id, last_seen_at, and deleted_at (soft-delete). On dataset rows: source_system, source_refcode, source_file_id, source_version, last_synced_at, and deleted_at.

Client & config layer

DigibatClient (digibat/client.py) wraps requests.Session with the DATALAB-API-KEY header and User-Agent: CellSeer/DigibatClient. Key behaviours:

  • get_json() raises RuntimeError on HTTP 401/403 or error-status payloads.
  • download() enforces a minimum 120-second timeout for file downloads and guards against HTML error-page responses.
  • Supported cycling file extensions: .xlsx, .xls, .csv, .mpt, .mpr. BDF cycle-block objects (blocks_obj) are also harvested as bdf-kind FileCandidate entries.

DigibatConfig (digibat/config.py) is a frozen dataclass holding base_url (default https://digibat.dept.ic.ac.uk), api_key, and timeout_seconds. Loaded from env vars DATALAB_BASE_URL, DATALAB_API_KEY, DATALAB_TIMEOUT. The router resolver _effective_config() prefers a per-project key stored in digibat_connection; falls back to the env var; raises HTTP 400 if neither is available.

Soft-delete / purge lifecycle

Deletion is two-phase:

  1. Soft-delete (phase 1): deleted_at is stamped on stale cells, files, and datasets at the end of each full sweep, or immediately when a file disappears from the upstream item. Records remain queryable but are excluded from normal views.
  2. Hard-delete / purge (phase 2): purge_soft_deleted() in provenance.py runs explicitly via CLI flag --purge (or a future admin endpoint). Configurable age cutoff defaults to 30 days. Purge order: dataset rows (local Parquet files unlinked first) → digibat_file_map rows → cell rows (cascades to digibat_cell_map).

Convergence with browser upload

DIGIBAT sync never writes a parallel storage format. After ingest_cycling_file:

  • cell and dataset rows match the upload path layout.
  • Parquet files land under the same data_lake/{project}/{cell_id}/ template.
  • Dashboard hooks (useCellRecordIndexQuery, useRatePerformanceQuery) see new data after triggerDataRefresh() — no DIGIBAT-specific query layer.

CLI alternate entry

backend/scripts/sync_digibat.py (and sync_service.run_sync_cli()) call sync_collections() directly without the HTTP router — useful for cron/ops. The CLI creates its own digibat_sync_run row when no run_id is passed. The run history (last 20 runs) is also accessible via GET /api/projects/{project_id}/digibat/runs.
