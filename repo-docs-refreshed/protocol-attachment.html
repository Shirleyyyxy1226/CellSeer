Protocol attachment

End-to-end trace of the two-step attach-protocol wizard — how segment JSON is persisted on cells and mirrored into cycling dataset metadata, and how dashboards consume it for filtering and protocol-gated metrics.

Related pages. Data model (protocol_segments columns) · Master Plot metrics (protocol-locked metrics).

Persistence model (no template FK)

Attaching a protocol does not set a protocol_template_id on the cell — there is no such column. The wizard may start from a template card (useProtocolTemplates), but save copies the segment list verbatim:

  • Source of truth: cell.protocol_segments (JSON text) and cell.protocol_name
  • Mirror: dataset.meta JSON field protocol on the cycling row when it exists — keeps rate-performance loaders working without re-querying cell columns
  • Templates: Separate rows in protocol_template (segments_json). Creating a template does not attach it; attaching does not reference template ids

Wizard structure

The attach wizard is a two-step modal (not three). A Stepper component renders completed steps as clickable for back-navigation:

  1. SequenceStep — user names the protocol and defines segments. Advancing to step 2 requires sequenceValid (all segments pass validation and at least one exists).
  2. ApplyStep — shows target cells and an overwrite review. Submit requires sequenceValid && cellIds.length > 0. On success, a SuccessPanel shows "x of y cells attached" and warns about any missing cell IDs.

Default seed. When no seedSegments are provided, the wizard initialises with two segments:

  • formation: cycleStart:1, cycleEnd:3, cRate:0.1
  • main cycling: cycleStart:4, cycleEnd:null, cRate:1.0 (open-ended)

Each subsequent segment's cycleStart is auto-derived from the previous segment's cycleEnd + 1 by makeBlankSegment().

Wire format

Segment JSON stored in cell.protocol_segments and mirrored to dataset.meta.protocol:

[
  { "name": "formation", "cycleStart": 1, "cycleEnd": 3, "cRate": 0.1 },
  { "name": "main cycling", "cycleStart": 4, "cycleEnd": null, "cRate": 1.0 }
]

The TypeScript type OpenEndedProtocolSegment (cellTypes.ts) is the index-API form where cycleEnd may be null. The downstream ProtocolSegment type (used in rate-performance payloads) requires both cycleStart and cycleEnd to be finite numbers.

Rate-performance responses expose resolved segments as protocolSegments on each cell payload. _parse_protocol_meta builds a cycle_to_rate map from segments, which gates which cycles receive a C-rate label in the plot. _materialise_protocol_segments converts open-ended segments into the closed ProtocolSegment form carried through the Master Plot pipeline inside summariseCell(). Protocol-gated Master Plot metrics (capacity retention, Coulombic efficiency, dQ/dV peak shift) require attached segments before they become selectable; values display as "Coming soon" once a protocol exists.

Segment validation rules

The same rules apply at both the template CRUD routes and the cell-level attach routes (shared via _validate_segments / _normalise_protocol_segments):

  • At least one segment must be present.
  • cycleStart ≥ 1
  • cycleEnd ≥ cycleStart when non-null
  • cRate > 0
  • Segments are sorted by cycleStart.
  • Adjacent segments must not overlap: segment i cycleEnd must be strictly less than segment i+1 cycleStart.
  • Names are trimmed and capped at 80 characters.

Related validation

Protocol attachment unlocks protocol-gated Master Plot metrics — capacity retention, Coulombic efficiency, and dQ/dV peak shift — which depend on correct segment boundaries and C-rate labels. The computations behind those metrics are validated on reference cell CEL-79 against Neware export sheets and published NMC622 dQ/dV peak positions.
